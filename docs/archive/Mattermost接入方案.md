# 知识库问答系统 → mm.maoke123.com 右侧栏接入方案

> 目标：在公司 Mattermost（`mm.maoke123.com/chat`）里，用**右侧栏独立面板**提供知识库问答。
> 前提：你有管理员权限；知识库问答系统目前还没有代码（全新开发）。

---

## 一、结论先行

**可以接，而且路子是标准的：写一个 Mattermost 插件。**

3 个事实决定了方案形态：

1. `mm.maoke123.com/chat` 是 **Mattermost** 的前端（`/chat` 是它的默认路径，页面标题被改成了「企业管理工作台」）。同域名的[《墨家 Mattermost 用户手册》](https://docs.mm.blackwings.com.cn/chapter3/1-from-weixin-to-mm.html)也印证了这一点。
2. Mattermost 是**开放集成**的：它的右侧栏（RHS）只能由**插件**占据，没有纯配置的办法，也没有"把网页挂到侧栏"的内置功能。所以"要侧栏面板"＝"要装插件"，这个绕不过去。
3. 你是管理员 → 装插件的门槛已经解决（上传 `.tar.gz` + 刷新页面）。

**推荐路线**：右侧栏里嵌一个 **iframe**，包住你自己的知识库 Web 应用。
插件本身极薄（几乎不写 Mattermost 业务代码），你的界面完全自由，后期想换成原生 React 面板也不返工。

---

## 二、整体架构

```
┌───────────────────────── 用户浏览器 ─────────────────────────┐
│  Mattermost Web (mm.maoke123.com)                            │
│    ├─ 右侧栏 RHS ── iframe ──► 知识库 Web 界面（你写）        │
│    └─ 频道头部按钮 / 斜杠命令 /kb                              │
└───────────────┬──────────────────────────┬───────────────────┘
                │ 页面加载插件               │ HTTPS / SSE 流式
                ▼                          ▼
     ┌──────────────────┐        ┌──────────────────────────┐
     │ Mattermost 服务器 │        │ 知识库服务 (FastAPI)      │
     │  + kb 插件         │        │  入库·切分·向量化·检索·生成 │
     │  (只做身份与入口)   │───────►│  PostgreSQL+pgvector 或   │
     └──────────────────┘  校验身份 │  Chroma；Ollama / API    │
                                   └──────────────────────────┘
```

三个组件，互相解耦：

| 组件 | 职责 | 技术选型 | 是否依赖 Mattermost |
|---|---|---|---|
| **知识库服务** | 文档入库、检索、生成、引用 | Python + FastAPI，SSE 流式 | 否，可独立运行和测试 |
| **知识库 Web 界面** | 提问、答案流、来源、文档管理 | React + Vite（窄栏优先） | 否，浏览器里可单独打开 |
| **Mattermost 插件** | 侧栏入口、频道按钮、`/kb` 命令、签发身份令牌 | `plugin.json` + webapp 打包 | 是 |

**关键好处**：前两个组件跟 Mattermost 完全无关。你先把知识库做成一个能用的网页，最后一天才用插件把它"挂"进侧栏。中间任何一步失败，知识库本身都不会白做。

## 三、右侧栏怎么做：两条路线

Mattermost 插件的前端 API 是 `registry.registerRightHandSidebarComponent(组件, 标题)`，返回 `toggleRHSPlugin` 用来开关面板。

### 路线 A：iframe 包页面（推荐先做）

```
RHS 组件 = <iframe src="https://kb.内网域名/?token=短期JWT" />
```

- 优点：你的界面想怎么做就怎么做；本地开发时直接在浏览器打开 `localhost:5173` 调试，不用碰 Mattermost；插件代码不到 100 行。
- 缺点：iframe 里的样式和 Mattermost 主题不联动；滚动条、右键菜单、剪贴板权限偶有割裂感。
- 前提：你的服务要允许被嵌入（响应头别设 `X-Frame-Options: DENY`，或写 `Content-Security-Policy: frame-ancestors https://mm.maoke123.com`）。

### 路线 B：原生 React 组件

- 优点：和 Mattermost 主题、字体、暗色模式完全一致，体验最好。
- 缺点：要按 Mattermost 的 webapp 打包规范构建（`@mattermost/client` 等依赖版本要跟服务器对齐），调试要起一个本地 Mattermost 或反复上传插件，迭代慢很多。

> **建议**：A 起步，B 收敛。因为两边都是 React，路线 A 里的业务组件（提问框、答案流、来源卡片）可以原样搬进路线 B 的插件包，只换外壳。先跑通，再美。

### ⚠️ 一个必须提前想清楚的限制

Mattermost 的右侧栏宽度是**固定的窄栏（约 400px）**，用户不能拖宽。所以：

- 侧栏里只做**问答对话流**（单列、窄）是很合适的；
- 如果你说的"完整界面"包含**表格、多列、文档管理大页面**，侧栏装不下。

处理办法（三选一，可组合）：

1. 侧栏只做入口 + 简版对话，复杂操作放"在新标签页打开"按钮（`window.open`）；
2. 插件在频道头部菜单里再加一个"打开知识库工作台"的全屏入口；
3. 较新版本的 Mattermost 支持**应用栏（App Bar）**，可以把应用做成全屏视图——需要先确认你们的版本是否支持。

这一点最好现在就定，它直接影响界面设计。

## 四、三个关键设计点

### 1. 身份与鉴权（别转发 Mattermost 的 token）

用户点开侧栏时，必须让知识库知道"他是谁"，才能做权限隔离（比如：销售只能查销售文档）。

**推荐做法**：
```
浏览器 → 插件后端 /token（带 Mattermost 会话）
插件后端 → 用 pluginAPI 校验调用者身份
        → 签发 5 分钟有效的 JWT（HS256，密钥存 plugin KV）
浏览器 → 用这个 JWT 调知识库服务
知识库 → 验签，拿到 userId / username / 角色
```
好处：Mattermost 的会话 token 永远不出内网边界，知识库服务也不依赖 Mattermost 的数据库。

### 2. 流式输出

知识库回答要"一个字一个字蹦出来"。用 SSE（`text/event-stream`）：

- 浏览器直接连知识库服务最好（最简单）；
- 如果知识库服务只有服务器能访问、浏览器访问不到，就得让插件后端做一次 SSE 转发——能work，但复杂度和故障点都会上升。

**所以"浏览器能不能直接访问知识库服务"这件事，请在开工前确认。**

### 3. 部署与网络可达性（最容易卡住的地方）

- **iframe 由浏览器加载** → 每台电脑都要能访问知识库地址。内网统一域名/IP 通常没问题；如果知识库跑在你自己电脑的 `localhost:8000`，那就只有你能用。
- **Mattermost 服务器不参与 iframe 加载**，所以不需要在服务器上开端口——这是 iframe 方案的一个便宜之处。
- 建议给知识库服务一个**内网域名 + HTTPS**（自签证书会让浏览器和 iframe 都报警）。

| 需要 | 现状 | 说明 |
|---|---|---|
| Python | ✅ `D:\Anaconda\python.exe` | 知识库后端直接用 |
| Node / pnpm | ✅ DSH 自带运行时 | 构建插件前端够用，不必另装 |
| Git | ✅ `D:\Git\Git\cmd\git.exe` | 拉插件模板 |
| PostgreSQL | ✅ 已安装 | 配 `pgvector` 扩展即可当向量库 |
| Ollama | ✅ 已安装 | 本地跑 bge-m3 做向量、qwen2.5 做生成 |
| **Go** | ❌ 未安装 | 插件**服务端**需要；若走"纯前端插件"可能不需要（待验证，见下） |
| **Docker** | ❓ 未知 | 官方模板用它交叉编译 linux 二进制 |

### 一个待验证的便宜方案：纯前端插件

Mattermost 的插件包通常包含"服务端 Go 可执行文件 + 前端 JS"。但如果我们的插件**只需要一个 iframe 外壳**，理论上可以做成**只有前端、没有服务端**的插件包——那样就完全不需要装 Go，只要 Node 打包，上传后刷新页面即生效。

这条路省掉整条 Go 工具链，但需要先花 30 分钟验证你们服务器是否接受无服务端的插件包（部分版本会校验 `server` 字段）。

- 验证不通过 → 装 Go 1.22，或用 Docker 跑官方模板的交叉编译，把插件编译成 `linux-amd64`（服务器大概率是 Linux）。
- 另外，如果坚持走原生 React 面板（路线 B），服务端那部分基本是必需的，Go 就绕不开了。

## 七、开工前必须确认的 4 件事

1. **确认它真是 Mattermost，并拿到版本号**
   浏览器打开 `https://mm.maoke123.com/api/v4/system/ping` → 返回 `{"status":"OK"}` 即确认。版本看响应头 `X-Version-Id`，或 System Console → About。
   *版本决定插件 API 与 `min_server_version`，也决定能不能用应用栏。*

2. **确认允许上传插件**
   System Console → Plugins → Plugin Management：`Enable Plugins` 和 `Enable Plugin Uploads` 都要是开启状态。若被关，先由你（或运维）打开。

3. **确认知识库服务放在哪里、浏览器能否访问**
   拿一台普通电脑，用浏览器访问知识库的候选地址（比如 `http://10.x.x.x:8000`）。打不开就得先解决网络/域名/证书。

4. **确认模型来源（这一步涉及数据合规）**
   公司文档能不能发给外部 API？如果能，DeepSeek 之类最省事；如果不能，就用本机 Ollama（`bge-m3` + `qwen2.5:7b/14b`），全内网闭环，但要接受推理速度。**这个决定会显著影响 M1 的实现和验收标准。**

## 八、风险清单

| 风险 | 影响 | 应对 |
|---|---|---|
| 站点其实不是 Mattermost | 方案整体作废 | 第七节第 1 步，5 秒可验 |
| 插件上传被禁用 | 装不进去 | 管理员开启，或改用 `mmctl`/服务器目录放置 |
| 浏览器访问不到知识库服务 | iframe 白屏 | 内网域名 + HTTPS；或退化为全屏新标签页方案 |
| 服务器是 Linux/ARM | 插件二进制不匹配 | 交叉编译对应架构；纯前端插件可规避 |
| 数据合规不允许外发 | 只能用本地模型 | 提前确认，避免 M1 返工 |
| 侧栏太窄装不下设计 | 体验打折 | 第三节末尾的三选一，先定界面边界 |
| Mattermost 升级 | 插件需重新适配 | 锁 `min_server_version`，升级前回归 |
